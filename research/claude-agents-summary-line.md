# The `claude agents` dynamic summary line

How the live one-line summary in the `claude agents` view is produced and controlled.
Verified directly by reading job-state files on disk (`~/.claude/jobs/<id>/`), not inferred.

---

## TL;DR

The dynamic summary in `claude agents` is the **`detail`** field in
`~/.claude/jobs/<id>/state.json`. It is generated from the **agent's own message
text** — distilled by the harness's classifier — not read from any config file.

Control it via:
- **narration** — your latest one-line "what I'm doing / what just happened" sentence becomes the live summary
- **terminal markers** — `result:` / `needs input:` / `failed:` on their own line flip the row's state and set the final summary

The row **title** is a separate knob: the `name` field, set with `-n`/`--name` (auto-generated otherwise).

---

## Anatomy of a row

Each row in the `claude agents` view has two independent parts, both stored in
`~/.claude/jobs/<id>/state.json`:

| Field    | What it shows                                       | How it's set                                |
|----------|-----------------------------------------------------|---------------------------------------------|
| `name`   | the title of the row                                | `-n`/`--name` flag, else auto-generated     |
| `detail` | the dynamic summary line ("what it recently did")   | derived from the agent's own message text   |

The "dynamic line" people ask about is **`detail`**.

---

## Where `detail` comes from

`detail` is **not** read from a config file. It is the agent's narration, distilled
by the harness's classifier. Evidence from live jobs on disk:

- The current job's `state.json` had
  `"detail": "The \`claude agents\` summary line comes from the \`description:\` field…"` —
  verbatim the `result:` line written the previous turn.
- Another job (`cfdd0997`) had
  `"detail": "how to kill a session: /stop (inside), claude stop <id> (shell)…"` —
  again, that agent's own summary sentence.

`timeline.jsonl` confirms the mechanism: each entry pairs a `state` + `detail` with
the text of the message that produced it.

**The classifier reads only the message text** — not tool output, not subagent reports.

---

## How to control it

You control the summary by **what the agent writes in plain text**. This is exactly
the protocol a background agent operates under:

- **While working** → `detail` is your latest one-line narration. Lead each turn with a
  crisp "what I'm doing / what just happened" sentence; that becomes the live summary.
- **`result:` on its own line** → sets `state: done` and makes that line the final
  summary. Make it self-contained — readable by someone who never saw the task.
- **`needs input:` on its own line** → sets the "needs input" state with that text.
- **`failed:` on its own line** → sets the failed state with the reason.

Plain "done"/"finished" prose is **not** detected — only the
`result:` / `needs input:` / `failed:` markers flip the terminal state. Everything
else is treated as narration.

---

## The title is separate

To control the row's **title** (not the summary), use the `name` field —
auto-generated by default (`nameSource: "auto"`), or set explicitly at launch:

```sh
claude -n "deploy watcher" ...      # or --name
```

---

## Source of truth

- `~/.claude/jobs/<id>/state.json` — holds `name`, `nameSource`, `detail`, `state`
- `~/.claude/jobs/<id>/timeline.jsonl` — append-only log pairing each state/detail with the message text that produced it
